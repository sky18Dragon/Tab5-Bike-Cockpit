## 2. 系统架构

五层,上层只依赖下层。App 之间不直接调用,通过服务和事件通信。

```
┌──────────────────────────────────────────────────────────────┐
│ 应用层   Home(Launcher)│ Navi │ Music │ Game │ Settings        │
├──────────────────────────────────────────────────────────────┤
│ 系统/框架  System Super 或自研 Launcher(T10)│ Agent: xiaozhi     │
│          system_core:App 安装/生命周期     │ agent_manager + MCP │
├──────────────────────────────────────────────────────────────┤
│ 服务层   Service Manager(本地调用 + 事件发布订阅)                 │
│   官方:wifi · audio(含 AFE) · device · display · storage · nvs · sntp │
│   自研:svc_location · svc_audio_focus · svc_safety · svc_route    │
├──────────────────────────────────────────────────────────────┤
│ HAL 层   hal_interface · hal_adaptor · Tab5 板级条目(新增)         │
│          esp_board_manager · m5stack_boards 的 Tab5 配置           │
├──────────────────────────────────────────────────────────────┤
│ 平台层   ESP-IDF 6.0.x · FreeRTOS · esp_hosted(P4)· C6 协处理器固件 │
└──────────────────────────────────────────────────────────────┘
```

### 2.1 App 与服务模型

- 每个功能一个 App(Brookesia native app),有独立 UI 与生命周期:安装、启动、暂停、恢复、退出
- 导航、音乐允许后台运行;游戏退出即释放内存
- 跨 App 通信走 Service Manager 的函数调用和事件订阅,例如 `svc_location` 发布位置,导航 App 和桌面迷你地图卡片都订阅
- 小智通过 MCP 工具调用服务函数:官方提供 `AddMCP_ToolsWithServiceFunction`,把现成服务函数直接注册成工具;需要定制时用 `AddMCP_ToolsWithCustomFunction`;不用时 `RemoveMCP_Tools` 注销
- 自研服务统一放在 `firmware/components/svc_*`,按 Brookesia 服务插件形式实现,方便被 MCP 直接引用

### 2.2 事件(沿用 v0.1 的主题名,实现上映射为 Service Manager 事件)

| 事件 | 发布者 | 载荷 | 订阅者 |
| --- | --- | --- | --- |
| `loc/fix` | svc_location | 经纬度(WGS-84)、速度、航向、精度、卫星数、时间 | Navi、Home 卡片、svc_safety、状态栏 |
| `loc/state` | svc_location | NO_FIX / FIXED / LOST | 状态栏、Navi |
| `net/state` | service_wifi | 断开 / 连接中 / 已连接,SSID,RSSI | 状态栏、小智、Music(电台) |
| `audio/focus` | svc_audio_focus | 当前焦点持有者 | Music、导航播报、小智 |
| `music/now` | Music | 曲目、进度、状态 | Home 卡片、小智 |
| `xz/state` | agent_xiaozhi | idle / listening / thinking / speaking | 浮层、状态栏、svc_audio_focus |
| `power/state` | service_device 或自研电源模块 | 电量、供电来源、温度 | 状态栏、Display |
| `ui/safety` | svc_safety | `RIDING` / `PARKED` | 所有 App(UI 闸门) |

`svc_safety` 订阅 `loc/fix`:速度 > 3 km/h 持续 N 秒进入 `RIDING`,低于阈值持续 M 秒回到 `PARKED`(迟滞,避免红绿灯处抖动;初值 N=2s、M=5s,实车后定)。定位丢失时:先保持上一状态,丢失超过 10 秒按 `RIDING` 处理(宁可多限制,避免误开放游戏)。所有安全规则 SAFE-01..04 只读 `ui/safety`。

## 4. 模块设计

### 4.1 板级与显示(M1,已落地)

板级(`firmware/boards/m5stack_tab5/`):

1. 基线是 `esp_board_manager 0.5.15` 自带的 `m5stack_tab5`。它用「聚合芯片」在运行时识别屏幕:按触摸地址和固件版本区分 ILI9881C(GT911,0x14)、ST7123(固件版本 3)、ST7121(固件版本 1),并给每种面板配各自的 DSI 时序。本机是 ST7121
2. 改动(为了适配 Brookesia 0.7 的 HAL 适配器):
   - 屏幕统一 RGB565(`bits_per_pixel: 16`)、3 个帧缓冲(`num_fbs: 3`)、`use_dma2d: false`;`setup_device.c` 不再对 ST7121 / ST7123 强制 24 位和单帧缓冲
   - 触摸依赖加上 `esp_lcd_touch`(`require: public`)
   - ES7210 加通道标签 `[NA, RE, FR, FL]`(沿用 esp_box_3 的写法,待核,见 06 的 T18)
   - 去掉摄像头设备和传感器配置(P2 功能)
   - `sdkconfig.defaults.board` 换成 Brookesia 0.7 的 Kconfig 名字(`GENERAL_DEVICE`、`STORAGE_GENERAL_FS_*` 等),并保留 Tab5 的 Flash / PSRAM / 芯片版本 / ESP-Hosted SDIO 引脚
3. 生成:`idf.py gen-bmgr-config -c ./boards -b m5stack_tab5`,产物在 `components/gen_bmgr_codes/`(不入库)
4. 已核对的引脚 [文档]:ESP-Hosted SDIO 的 CMD=13、CLK=12、D0..D3=11..8、C6 复位=15;音频 I2S 的 MCLK=30、BCLK=27、WS=29、DOUT=26、DIN=28;I2C SDA=31 / SCL=32;背光 LEDC 通道在 G22;SD 卡 SDMMC 4 线,LDO 通道 4 供电;MIPI LDO 通道 3(2.5V)

显示:

- 面板原生**竖屏 720×1280**,帧缓冲 RGB565 约 1.76MiB × 3;M1 基线以竖屏出画面
- 横屏:示例的 `main/modules/display/display.cpp` 里 `ESP_LV_ADAPTER_ROTATE_0` 是应用代码,改成 `ROTATE_90`(并交换逻辑宽高、校正触摸映射)即可,需要实机验证帧率,放在 M2(06 的 T17)
- P4 推荐配置 [文档]:`CONFIG_CACHE_L2_CACHE_256KB=y`、`CONFIG_CACHE_L2_CACHE_LINE_128B=y`、`CONFIG_SPIRAM_XIP_FROM_PSRAM=y`、`CONFIG_COMPILER_OPTIMIZATION_PERF=y`、`CONFIG_FREERTOS_HZ=1000`、`CONFIG_LV_DEF_REFR_PERIOD=15`。M1 的板级默认用的是 L2 缓存 128KB(与 Brookesia 的 P4 板一致),256KB 留到实机帧率测试时对比
- 基线 [推算]:P4 MIPI-DSI 1024×600 RGB565 约 55fps,1280×720 像素约 1.5 倍,估计 35–45fps;旋转后需实测

### 4.2 Launcher / 系统壳(M2)

- System Super 只在 Brookesia v0.8,而 v0.8 与 Tab5 的 P4(rev<v3)在 IDF 6 上被 `esp-sr` 卡住(ADR-0004),所以 **Launcher 自研**
- 基于 `service_manager` 的服务调用 / 事件,加 LVGL 自绘:Dock(宽 120px)、状态栏(48px)、卡片区;左边缘右滑返回、卡片订阅事件刷新、两套主题(浅 / 深)
- 示例工程里的 Display 模块(表情主屏 + 设置页)作为起点,小智状态、对话浮层沿用
- Settings:先扩展示例自带的设置页(Wi-Fi、亮度、音量、Agent 切换),再加 GPS 状态、地图目录、小智服务地址

### 4.3 小智集成

- `brookesia_agent_manager` + `brookesia_agent_xiaozhi`;chatbot 示例为起点,M1 原样跑通
- 默认半双工:Agent 说话时不听,可被唤醒词打断,满足「打断」需求;连续对话由 Agent 状态机管理
- 唤醒词:配置为「你好小智」,可用模型 `wn9_nihaoxiaozhi_tts`、`wn9l_nihaoxiaozhi_tts3`、`wn10_nihaoxiaozhi` 等;烧入 `model` 分区;阈值可调(`set_wakenet_threshold`);Brookesia 唤醒词配置项默认留空 = 由 Audio 服务自动识别
- 对话浮层是系统壳的 overlay;导航时限高为屏幕 1/3
- MCP 工具:优先把服务函数直接注册为工具,统一返回 `{ok, result | error_reason}`;handler 不阻塞语音任务
- 离线:`net/state != connected` 时本地提示「当前无网络」,不尝试连接
- 官方激活流程沿用(`esp_xiaozhi` 的 keystore 使用 NVS)

### 4.4 音频与焦点

Audio 服务持有 ES8388 输出,各使用者通过「流」申请:

| 流 | 优先级 | 抢占行为 |
| --- | --- | --- |
| 小智语音 | 最高 | 音乐压低到 20%(duck),不暂停 |
| 导航播报 | 高 | 音乐压低到 20%;与小智同时到达时小智优先,播报排队 |
| 音乐 | 普通 | 被压低,结束后渐变恢复 |
| 提示音 | 低 | 不抢焦点,混音 |

- 状态:`IDLE → MUSIC → DUCKED(by XZ/NAV) → MUSIC`;小智说话结束后延迟 300ms 再恢复,避免连续对话时音量抖动
- 采集侧:ES7210 双麦 + AFE(AEC / VAD / WakeNet),AEC 参考取自播放通道;音乐播放中唤醒要在 M2 实测
- 音量:主音量 × 流音量;音量归 `service_device` 管(Brookesia v0.7.6 起)
- 音乐解码:P0 先验证 `service_audio` 能否直接播 SD 卡 MP3 / AAC / FLAC(T15);不行则自建播放链路(解码组件 + I2S 输出),但与 AFE 共享同一输出和 AEC 参考
- 硬件上限:NS4150B 1W @ 8Ω;风噪下不够响时,方案依次为:EQ 提升中频、调高上限并加削峰保护、3.5mm 耳机口外接(T7)

### 4.5 Location 服务

1. UART 任务读 NMEA(PORT.A,115200 8N1),按行解析 `GGA` / `RMC`,`GSV` 取卫星数
2. 过滤:无效定位、HDOP 过大、速度尖峰丢弃
3. 速度低于约 1 km/h 时航向保持上次有效值,防止原地漂移
4. 发布 `loc/fix`;丢失 3 秒内发 `loc/state = LOST`
5. 最后有效位置每 30 秒或停车时写 NVS,开机先显示上次位置
6. 刷新率默认 1Hz,可配到 5–10Hz;改率 / 波特率需向模组发 CASIC 指令,指令集 [待核],先对照协议手册
7. 上电顺序:`EXT5V_EN` → 等待 GPS 启动 → 开 UART;`EXT5V_EN` 失败要在状态栏报「GPS 无电」,与「无信号」区分

### 4.6 导航与地图(M3 / M4)

以 `map_tiles` v2 为核心,不自写瓦片缓存和路线匹配(ADR-0003)。

地图:

- `map_view` 作为导航 App 的主控件,`map_view_set_tile_source("/sdcard", "tiles1", slots, true)`,缩放范围用 `map_tile_cache_probe_zooms()` 探测 SD 卡实际拥有的级别后夹取
- 缓存槽数:视图约 1160×672,[推算] 同屏约 24 块、加预取环约 48 块,基线 48 槽(6MB),出现占位图则升到 64 槽(8MB);要在 M3 实测并写回
- 跟随:`map_view_set_follow(true)`,`map_view_set_follow_offset()` 让车标靠下;拖动会取消跟随并发出 `LV_EVENT_VALUE_CHANGED`,App 据此做「10 秒无操作自动回到跟随」
- 方向:P0 为北向上 + 车标按航向旋转(`map_view_set_position(..., heading, ...)`);「跟随车头」转图为 M3 实验项,走 PPA 旋转,[推算] 理论上限 27–45fps,不达 20fps 就放弃
- 线程:所有 `map_view_*` 调用持 LVGL 锁;`map_tile_cache_get()` 只在 LVGL 线程调用;GPS 回调只投递事件,不直接调视图

路线(P1):

- `route.bin` 由 PC 端生成(OfflineMapDownloader 的 `app_nav.py`,或 `route_format.py --gpx`),放 SD 卡 `routes/`
- 每个定位调用 `map_route_match()`,拿到是否在线、横向偏差、下一机动点及距离、剩余距离;偏航时进度冻结(组件设计如此),UI 提示「偏离路线」并显示回归方向(`map_geo_angle_diff_deg`)
- 语音播报:阈值(如 200m / 50m / 到达)触发,文案经导航播报流
- 路线类型:点到点用 DRIVE(到达判定),骑行训练闭环用 EXERCISE(圈数)

在线规划(P1):

- `self.navi.navigate_to` → `RoutePlanner` 后端(高德骑行 API 或 Valhalla)→ 折线与步骤 → 转 WGS-84 → 端侧写出 `route.bin` → `map_route_load()`
- 高德返回坐标需 GCJ-02 → WGS-84 转换(T9);需要一个 C 版 `route.bin` 写入器(对照 `map_route.h` 头文件布局,M4 开工时确认)
- 失败回退:无网络或 API 失败时提示,并允许选择 SD 卡上已有路线
- Key 不入库,见第 8 节

### 4.7 数据格式与存储布局

SD 卡(按 `map_tiles` 与 OfflineMapDownloader 的实际约定):

```
/sdcard
├── tiles1/{z}/{x}/{y}.bin     离线瓦片:12 字节头 + 256×256 RGB565(每块约 128KiB)
├── routes/*.bin               离线路线(map_route 的 route.bin)
├── routes/*.txt               路线说明(PC 工具生成)
├── music/                     本地音乐
├── radio.json                 网络电台列表(P1)
├── logs/crash-YYYYMMDD.log    崩溃日志
└── ATTRIBUTION / README.txt   地图数据署名(PC 工具写入,界面「关于」页展示)
```

容量 [推算]:每 1000 块瓦片约 128MiB;缩放每加一级同区域瓦片约 ×4;先用走廊模式只下载常骑路线。

`route.bin`:使用 `map_route` 的格式(每点 16 字节含 `min_zoom`,每转向 20 字节,10000 点约 160KB),**本项目不再自定义格式**。

NVS 命名空间:

| 命名空间 | 内容 |
| --- | --- |
| `wifi` | 最多 5 个 SSID / 密码 / 优先级(也可用 `service_wifi` 自带存储) |
| `xiaozhi` | 服务地址、激活状态、唤醒词开关 |
| `ui` | 亮度、主题、音量(主 / 音乐 / 语音) |
| `music` | 上次曲目、播放位置 |
| `navi` | 上次位置、收藏点、地图模式、规划后端选择 |
| `sys` | 上次 App、OTA 状态 |

### 4.8 Flash 分区(草案,16MB)

| 分区 | 大小(约) | 用途 |
| --- | --- | --- |
| nvs | 24KB | 配置 |
| otadata / phy_init | 8KB / 4KB | |
| ota_0 / ota_1 | 各 4.5MB | 主固件(双分区 OTA) |
| model | 约 2MB | ESP-SR 唤醒词 / VAD 模型;大小随所选模型定 |
| storage(LittleFS) | 约 4MB | System Super 资源、字体、图片、提示音 |

合计约 15MB,留约 1MB 余量。**M1 实测**:基线固件 `tab5_bike_cockpit.bin` 为 6,427,056 字节(约 6.13MiB),放进示例的 7MB factory 分区仅余 12%;按这个体积 16MB Flash 放不下两个 OTA 分区(见 06 的 T19)。所以上表的双 OTA 分区是目标而不是现状,M4 做 OTA 前要先瘦身(关 Coze / OpenAI、去未用组件)或换方案。

### 4.9 BLE 遥控器(P1)

- 控制器在 C6,P4 跑主机栈;官方有 NimBLE over Hosted HCI 与 Wi-Fi 共存示例,先照它搭
- 首期设备:BLE 媒体按键 / 车把遥控器(播放、切歌、唤醒小智)
- P4 侧是否带现成 HID 主机角色未查到(T14),M4 先用一台实际遥控器验证;若无现成支持,按其 GATT 自定义解析
- 按键映射放 NVS,可在设置页改;Safety 闸门不限制 BLE 按键
- 不做经典蓝牙

### 4.10 电源与热管理

- 电量与功率:INA226 读电压 / 电流;`service_device` 的电量接口若够用就复用
- 低电量:提示早于保护线;电池 <6V 会进保护模式需特殊恢复 [文档],所以固件在远高于 6V 时就降背光并安全关机,具体阈值用实测放电曲线确定
- **关机不充电** [文档]:UI 提示「USB 供电需开机」;充电状态在状态栏显示
- 工作温度 0–40°C [文档]:过热降背光并提示;低温(<5°C)提示电池 / 屏幕性能下降;温度源用板载传感器(IMU 或 RTC 的温度输出是否可用 [待核])
- 断电恢复:`sys` 记录上次 App 与曲目

### 4.11 可靠性与日志

- 任务看门狗 + 崩溃日志(摘要)写 SD 卡 `logs/`
- C6 失联检测:ESP-Hosted 心跳超时 → 复位 C6(经 IO 扩展器)→ 重连 Wi-Fi
- 日志分级,默认 INFO;骑行测试开启关键事件日志:定位丢失、唤醒、焦点切换、内存水位、温度、电压

### 4.12 OTA(P1)

- P4:双分区 OTA,启动后自检通过才标记有效,失败自动回滚
- C6:经 ESP-Hosted 总线升级(HTTPS / LittleFS / `slave_fw` 分区三种来源),版本比较后才写;C6 固件 ≥v2.6.0 时有 `OTA_ACTIVATE` 步骤;**升级完成后主机重启**
- 版本绑定表:P4 固件版本 ↔ 最低 C6 固件版本;启动时读取 C6 版本,不满足则提示升级
- 来源:局域网 / 自建服务器 URL(设置页配置),不依赖第三方
- Tab5 出厂 C6 固件版本先读出来记录(M1)

## 6. 任务与线程模型(草案)

| 任务 | 说明 | 优先级倾向 |
| --- | --- | --- |
| Audio 播放 / 采集 / AFE | I2S 读写、解码、AEC、WakeNet | 最高(防爆音) |
| LVGL / UI | 渲染与输入 | 高 |
| 小智 Agent | 上传、播放、MCP | 中 |
| Location | UART 读与解析 | 中 |
| Map tile loader | `map_tile_cache` 自带后台线程,读 SD | 低 |
| Network | Wi-Fi 管理、重连 | 中 |

原则:UI 任务内不做阻塞 IO;共享 I2C 总线访问串行化;P4 双核,音频与 UI 尽量分核,最终以实测为准。
