# 08 显示黑屏排查

日期:2026-10-19(2026-10-20 更新实验结果)。状态:**已解决(实验 F,2026-10-20):LCD_RST 必须推挽拉高**;热启动和冷启动后屏幕、触摸都正常。以下为排查过程中记录的原始现象:背光亮、屏幕全黑;触摸、Wi-Fi、音频、SD 卡的驱动日志均正常。M5Burner 烧录官方出厂固件后屏幕和触摸都正常,硬件无故障,见第 7 节。**根据官方 Demo 的重新分析见第 9 节**:最可能的原因是 LCD_RST 的拉高方式。

## 2. 已确认的事实

1. 芯片 ESP32-P4 rev v1.3(rev<v3),屏幕为 **ST7121**(触摸固件版本 1)。**[日志]**
2. 触摸控制器在 0x55 上应答,能读出固件版本。~~说明这颗芯片已出复位~~(更正:触摸一侧由 TP_RST 控制,LCD_RST 是另一根线,触摸应答不能说明显示部分已出复位)。**[日志]**
3. 背光(G22 PWM)工作正常,屏幕背光亮。**[用户]**
4. DSI 总线创建成功,面板创建、`reset`、`init`、`disp_on_off` 的调用都没有返回错误(只有 `swap_xy` 不被支持的警告)。**[日志]**
5. 往 DPI 帧缓冲写入数据成功,面板上没有任何图像。**[用户] [日志]**
6. 我们使用的 ST7121 初始化表与官方 Demo、Espressif esp-bsp、M5GFX 的表**逐字节一致**(含末尾 `SLPOUT 等 80ms → DISPON 等 800ms`)。**[源码]**
7. `esp_lcd_st7121`(注册表 1.0.1)与 `esp_lcd_st7123` 的 `reset`、`init` 逻辑在重命名后**完全相同**。所以 Espressif BSP 用 ST7123 驱动跑 ST7121,和我们用 ST7121 驱动,行为没有区别。**[源码]**
8. 注册表 `esp_lcd_st7121 1.0.1` **自带的**默认初始化表末尾是 `SLPOUT 等 120ms、DISPON 等 0ms`,与上面三方不同。我们已经改为传入官方表。**[源码]**

## 5. 问题点(按可能性排序)

### 5.1 复位释放后到第一条 DCS 命令的时间太短(最可疑)

- 证据:我们约 130ms;Espressif BSP 在使能后固定等 **500ms**;M5GFX 在释放后等 100ms + 触摸固件轮询 + 80ms。M5GFX 注释明确说 ST71xx 复位后恢复很慢。
- 关键点:**触摸部分能应答 I2C,不代表显示部分已经准备好接收 DCS 初始化命令**。我们的触摸探测成功只能证明触摸一侧就绪。
- 与你的时间线吻合:热状态下芯片没有被真正复位过,初始化命令即使太早也"碰巧"生效;冷启动时就丢命令,结果是背光亮、面板没初始化、全黑。
- 这是**假设**,没有被实验证实。

### 5.2 LCD_RST 的终态与官方不同

- 官方终态:P4 为**输入 + 上拉**(DIR=0x6F)。我们读回的终态:DIR=0x7F、OUT=0x66、HIZ=0x90,即 P4 是「输出,输出值 0,但 Hi-Z,上拉使能」。
- 原因:`esp_io_expander` 的基类按它缓存的寄存器值回写 DIR / HIZ,把我们用原始 I2C 写入的 0x6F 改回了 0x7F。
- 电气上应等价于释放(触摸一侧已应答,说明芯片出了复位),但 PI4IOE5V6408 的上拉在「Hi-Z 输出」模式下是否生效,没有核实。**未排除**。

### 5.3 DSI 链路参数与 DCS 读写

- 我们没有读回过面板的状态寄存器。**能否通过 DCS 读到面板、面板是否处于睡眠退出 / 显示开启状态,是目前最缺的证据**(下一步实验 A)。
- 其它未排除项:帧缓冲数(我们 3,参考实现 1~2)、DMA2D(我们关)、Frame ACK / 时钟通道 HS 策略(M5GFX #334)。

### 5.4 已基本排除

- LVGL / 表情 UI:关闭 UI 后直写帧缓冲仍黑。
- 初始化表内容:四方一致。
- 驱动选择(st7121 vs st7123):逻辑一致。
- 电源:电池 7.74V 稳定。
- 触摸 / I2C / C6 链路:均已恢复正常。
- 像素格式 / 时序数值:与参考实现一致。

## 7. 实验结果(2026-10-20)

| 编号 | 结果 | 来源 |
| --- | --- | --- |
| D | 自己用 `CONFIG_ESP32P4_SELECTS_REV_LESS_V3=y` 重编的官方 Demo 烧录后**仍然全黑**(背光亮) | [用户] |
| A | 诊断固件已烧录、正常启动,但前两次串口抓取里**没有出现 `PANEL` 行**(日志到 9.3s 停止,原因未定:DCS 读可能阻塞、或抓取被 DTR/RTS 复位打断)。**没有得到面板寄存器数据** | [日志] |
| 新 | 用 **M5Burner 烧录官方出厂固件**后,**屏幕能显示、触摸正常** | [用户] |

由此得到的事实与推论:

1. **面板和触摸硬件是好的**。「硬件损坏」「必须拔电池断电」这两类原因排除。**[用户]**
2. 同一块机器上,M5Burner 的出厂固件能显示,而「我们从源码重编的官方 Demo」全黑。差别可能在:(a) 出厂镜像与源码仓库版本不同;(b) 重编时为 rev v1.3 改的配置(`REV_LESS_V3` 等)影响了显示相关的时序或内存;(c) 烧录前面板处于卡死状态,M5Burner 的整片写入 / 复位顺序恢复了它。这三点**目前无法区分**。
3. 因此「重编官方 Demo 也黑」不再能证明"只有硬件问题"。它把问题范围缩小到:**这台 rev v1.3 机器上,从源码构建的固件**与**出厂镜像**之间的差异。

### 实验 A 结果(2026-10-20,干净版固件在已恢复的面板上仍然全黑之后)

先说明一个发现:`esp_lcd_panel_io_rx_param` 在 IDF 5.5.3 里用的 `mipi_dsi_hal_host_gen_read_short_packet` 有两处**无超时的死循环**(等 `read_cmd_busy` 清零、等读 FIFO 非空),面板不应答就永远卡住。所以上一次诊断固件没有任何 `PANEL` 输出。这次改为直接读 DSI 主机寄存器,并用带超时(100ms)的自写读。

| 项 | 读数 | 含义 |
| --- | --- | --- |
| `pwr_up` / `phy_rstz` | `0x1` / `0xf` | DSI 主机已上电,D-PHY 已出复位 |
| `phy_status` | `0x1529`(读之前) | PLL 已锁定(bit0);各数据通道和时钟通道都**不在 stop 状态**,即正在 HS 发送视频流 |
| `mode_cfg` | `0`(读之前) | 视频模式,在持续输出 |
| `vid_mode_cfg` | `0xff02` | burst 模式;**bit14 `frame_bta_ack_en` = 1**(每帧要求面板应答) |
| `lpclk_ctrl` | `0x3` | **`auto_clklane_ctrl` = 1**:空闲时时钟通道会回到 LP(M5GFX 的 ST7121 配置是强制 HS 时钟,见 4 节 #334) |
| `pckhdl_cfg` | `0x19` | BTA 接收**默认关闭**(`bta_en` = 0) |
| `int_st0` | 第一次读到 `0x00100000`,之后为 0 | bit20 = `dphy_errors_4`:曾经出现**数据通道 0 的 LP1 竞争**(读后清零,发生时刻不明);没有任何 `ack_with_err`(面板没有回错误) |
| `int_st1` | 0 | 没有超时 / ECC / CRC 错误 |
| 超时计数器 | `to_cnt` / `bta_to` / `lp_rd_to` 全为 0 | 所有 BTA / 读超时都被关闭 |
| 四次带超时的 DCS 读(0x0A、0x0D、0x0C、0x04) | 全部 `busy_done=0 data_arrived=0`;读完后 `cmd_pkt_status` 的 `rd_cmd_busy`=1,`phy_status` 的 `phydirection`=1 | 主机把总线交给面板后,**面板一直没有返回数据**,主机停在反向等待 |

结论(只写读数能支持的部分):

1. **主机侧没问题**:DSI 主机在以我们配置的参数发 HS 视频流,没有 ECC / CRC / 超时错误,面板也没有回 ACK 错误。
2. **面板侧状态读不到**:这块面板在 BTA 后不返回任何数据。可能是 ST7121 在这条总线上根本不支持 DCS 读,也可能是面板没有处于能应答的状态,**这一个实验分不开这两种情况**(官方 Demo、Espressif BSP、M5GFX 都没有读面板的代码)。因此没有拿到「面板是否已退出睡眠 / 显示是否已开启」的直接数据。
3. 新增两个与 M5GFX #334 对应的怀疑点:**Frame BTA ACK 开启**、**时钟通道自动回 LP**。ST7121 是 TDDI,时钟通道在消隐期回 LP 时可能无法保持同步。**这是假设,尚未验证**。
4. `dphy_errors_4`(LP1 竞争)说明初始化期间数据通道 0 上出现过电气冲突,可能与复位释放时面板侧的状态有关,发生时刻需要进一步定位。

### 补充:用 JTAG 读 DSI 主机寄存器(干净版固件,开机约 1~2 分钟后)

OpenOCD 经 USB-JTAG 能直接读外设(`mdw 0x500A0000`),所以**不用再改固件就能看主机状态**。读到的关键值:

- 视频时序寄存器与 900Mbps 的换算吻合:`vid_pkt_size`=720(0x2d0)、`hsa`=3、`hbp`=64、`hline`=1289(0x509)、`vsa`=20、`vbp`=24、`vfp`=200、`vactive`=1280(0x500);`dpi_color_coding`=0(RGB565)。**主机的视频参数没有算错**。
- 最后一条发出的命令头 `gen_hdr`=`0x2905`,即 DCS `0x29`(显示开),说明初始化序列完整发完了。
- `lpclk_ctrl`=3、`vid_mode_cfg`=`0xff02`、`pckhdl_cfg`=`0x19`,与诊断固件读数一致。
- `phy_status`=`0x15ab`:这次 `phy_direction`(bit1)=1、第 1 路数据通道处于 stop 状态,与诊断固件读读之前的 `0x1529` 不同。**原因未定**(可能是运行时间不同,也可能是 OpenOCD 接入造成的干扰),不能据此下结论。
- `int_st1`=`0x880`:bit7 `dpi_pld_wr_err`(DPI 像素 FIFO 写错误)和 bit11 `gen_pld_rd_err`。bit11 是我读 `gen_pld_data` 寄存器时弹空读 FIFO 造成的,**是读操作自己引入的**;bit7 是否真实存在、何时出现,没有定位。再读一次两个状态寄存器都已清零(读后清除)。

### 补充:用 JTAG 实时改 DSI 寄存器(2026-10-20,不重新烧录)

复位后用 `reset run` 重新启动干净版固件,持续读状态寄存器:`phy_status` 在 `0x1529 / 0x15b9 / 0x15bd` 之间不停变化,说明视频流一帧接一帧在发(消隐期通道回到 stop 状态),**没有卡在反向等待**。上一节里稳定不变的 `0x15ab` 是 OpenOCD 刚接入时的状态,不能当作固件运行时的状态。复位后 `int_st0` 只出现过一次 `dphy_errors_4`(LP1 竞争),`int_st1` 始终为 0。

然后每步保持 12 秒,**你观察屏幕**:

| 步骤 | 操作 | 屏幕 |
| --- | --- | --- |
| 0 | `vid_mode_cfg` 置 `vpg_en`(DSI 主机自带彩条,**不经过 DPI 和帧缓冲**) | 全黑 |
| 1 | `lpclk_ctrl` 改为 `0x1`(时钟通道强制 HS) | 全黑 |
| 2 | `vid_mode_cfg` 清掉 `frame_bta_ack_en` | 全黑 |
| 3 | 重发 DCS `0x11`、150ms 后 `0x29`(视频模式下发送,寄存器 `dpi_lp_cmd_tim`=0,这两条是否真的被发出**没有确认**) | 全黑 |

可以得出的结论:

1. **帧缓冲、LVGL、DPI 通路、DMA2D 都不是原因**。步骤 0 的彩条由 DSI 主机直接生成,面板仍然什么都不显示。
2. 「时钟通道自动回 LP」和「Frame ACK」这两个怀疑点,单独改掉都没有让屏幕亮,**基本排除**。
3. 剩下的问题在面板一侧:面板没有处于能显示 DSI 视频的状态。可能的原因有三类:(a) 初始化命令没有被面板接受(时序太早,或者之后又被复位冲掉);(b) 面板的复位 / 电源状态不对(LCD_RST 终态、数据通道上出现过的 LP1 竞争都指向这一类);(c) DSI 链路在面板端没有锁定(通道速率、通道数)。**目前没有数据能区分这三类**。
4. 同一块机器上出厂固件能显示,所以问题一定能由软件复现 / 修复。

### 补充:JTAG 重放初始化命令(失败)

复位后等约 30 秒,用 `tools/jtag/dsi_reinit.py` 切到命令模式重放 30 条官方初始化命令。**命令没有发出去**:命令 FIFO 一直排不空(`gen_cmd_full`=1),DPI 像素 FIFO 同时满(`dpi_pld_w_full`=1),`phy_direction`=1 且保持不变,`int_st1` 报命令写溢出和 DPI 写溢出。也就是说**主机发送引擎整个停住了**,屏幕自然没有变化。这条路在不重新烧录的前提下走不通;更像是主机在视频模式中途切到命令模式,或 BTA / ACK 在面板那一侧没有回应,总线停在反向状态。**原因没有进一步定位**。

## 9. 根据官方 Demo 重新分析(2026-10-20)

### 9.1 「重编的官方 Demo 也黑」不能说明面板有问题

| | 官方 README 要求 | 我重编时用的 |
| --- | --- | --- |
| ESP-IDF | **v5.4.2** | **v5.5.3**(为了能烧到 rev v1.3,又加了 `CONFIG_ESP32P4_SELECTS_REV_LESS_V3`) |
| 源码版本 | 发布版 V0.4(2026-06-02 构建,GitHub Release 与 M5Burner) | master `b4e356b`(2026-09-15,含 fix-lcd-rst,版本号 V0.5,**没有发布二进制**) |

所以「M5Burner 能显示、重编的 Demo 全黑」比较的是两套不同的东西:IDF 版本不同,LCD_RST 的处理方式也不同。

### 9.2 IDF 5.4.2 与 5.5.3 的 MIPI DSI 代码对比(已排除)

下载 v5.4.2 的 `esp_lcd/dsi/*`、`hal/mipi_dsi_hal.c`、`hal/esp32p4/include/hal/mipi_dsi_*_ll.h`、`clk_tree_defs.h` 逐个比对:

- DSI 主机寄存器层、D-PHY 寄存器层:**完全相同**。
- PHY 时钟:5.5 拆成「配置时钟」和「PLL 参考时钟」,但 rev<3 芯片走 `LEGACY` 分支,两者都是 20MHz PLL,**与 5.4.2 等价**。
- 桥接层:按芯片版本重新组织,rev<3 + RGB565 写入的寄存器值相同。
- 其余差异:定时时钟分频改为四舍五入(900Mbps 时转义时钟 22.5MHz → 18.75MHz;965Mbps 时两版相同)、水平时序补偿、帧缓冲分配方式。都不影响「面板完全不亮」。

更关键的反证:**我们第一次烧录用的也是 IDF 5.5.3,屏幕能显示表情**。所以 IDF 版本不是原因。

### 9.3 驱动与初始化流程对比

- 官方本地的 `esp_lcd_st7121` 与注册表 1.0.1:除格式和 `set_gap` 外**逐行相同**(复位都是 SWRESET + 120ms;初始化都是逐条发送、每条后等 5ms;默认表相同)。
- 官方 ST7121 路径:`init_cmds = NULL`(用驱动内置表)、`bits_per_pixel = 24`(驱动不用它)、DPI RGB565、`num_fbs = 1`、`use_dma2d = true`,之后只调用 `reset → init → disp_on`。
- board manager 在 `init` 之后**额外**发送 `MADCTL(0x36)`(镜像),必要时还会发 `INVON`,官方不发。这是次要差异,先记下。

### 9.4 LCD_RST 的拉高方式:与所有现象吻合

PR #18(fix-lcd-rst,`0e54f8f`)之前,`bsp_io_expander_pi4ioe_init` 把 P0~P6 都设为推挽输出,`OUT_SET = 0b01110110`,**LCD_RST(P4)推挽输出高电平**;`bsp_reset_tp` 把 P4、P5 一起拉低 100ms,再一起拉高。PR #18 之后才改成「P4 锁存 0,释放时切为输入 + 内部上拉」。**[源码]**

| 固件 | LCD_RST 拉高方式 | 屏幕 | 来源 |
| --- | --- | --- | --- |
| 我们第一次烧录(`2d7af49`,上游 board manager 配置:P4 输出、电平 1) | 推挽高 | **能显示** | [用户] [源码] |
| M5Burner 出厂固件(V0.4) | 推挽高 | **能显示** | [用户] [源码] |
| 重编的官方 master(V0.5) | 输入 + 上拉 | 全黑 | [用户] |
| 我们 `fc20edc` 之后的所有版本 | 输入 + 上拉 | 全黑 | [用户] |

这个假设还能解释其它现象:面板显示部分一直处于复位中,所以 DCS 读(BTA)没有任何应答、DSI 自带彩条也不显示、请求 ACK 的命令会让主机停在反向等待;触摸由独立的 TP_RST 推挽拉高,所以一直正常。**这仍是假设,需要实验 F 验证。**

风险:M5 在 PR #18 和文档里说推挽 3.3V 驱动 1.8V 的复位脚会漏电、可能扰乱 I2C。但已发布的出厂固件(包括你刚用 M5Burner 烧的)一直就是这样驱动的。

### 9.5 实验 F(已烧录:屏幕有显示)

- `setup_device.c`:扩展器 0x43 按 V0.4 初始化(P0~P6 推挽输出,`OUT_SET = 0x76`),再把 LCD_RST 和 TP_RST 一起拉低 100ms、拉高后等 100ms;删除「强制输入」;面板初始化前额外等 500ms;保留扩展器寄存器和引脚电平日志。
- `board_devices.yaml`:P4 重新列为输出、电平 1,与 `2d7af49` 相同。否则驱动用缓存回写输出寄存器时会把 P4 写回 0。
- 判定:屏幕亮 → 第 9.4 节成立;仍然黑 → 看日志里的 `LCD_RST pin=`,再去查 9.3 的 MADCTL 差异。

结果(2026-10-20):烧录后**屏幕有显示**。**[用户]** 第 9.4 节的假设成立:在这台机器上,LCD_RST 用「输入 + 内部上拉」释放时面板显示部分不工作,推挽拉高后正常。

日志里扩展器 0x43 的读数:`DIR=7f OUT=76 HIZ=80 PULL_EN=7f PULL_SEL=7f IN=00`。**[日志]** 前三项与预期一致(P4 为输出、输出 1、只有 P7 高阻)。`IN=00` 与 P4、P5 实际为高相矛盾,说明 PI4IOE5V6408 的输入状态寄存器**读不到输出脚的电平**,所以日志里的 `LCD_RST pin=` 没有参考价值,应删除。

冷启动复测(2026-10-20):双击电源键关机、等 5 秒、单击开机后,**屏幕有显示,触摸正常**。**[用户]** 同时抓的串口日志里只有一段连续运行(打开串口时 Tab5 自己热重启了一次,从 0 运行到 57 秒,中间串口没有断开),**没有抓到冷启动那一次**;这一段里触摸以 IRQ 模式初始化成功,并记录到滑动手势 `ScrollRight` / `ScrollLeft`,界面从表情页切到了设置页。**[日志]**

未做:二分「500ms 额外等待」是否必要(目前保留,它属于已验证的配置);删除诊断日志。
